read; every behavioural claim about the git hooks was reproduced in throwaway
repositories that point `core.hooksPath` at this repo's `.githooks/` (the same

## 1. Git hooks and enforcement

### 1.1 `FORBIDDEN_MSG_RE` matches substrings and has no exemptions (priority 1)

Verified blocked for an agent: `Clarify push rule in AGENTS.md`,
`Rename CLAUDE.md section`, `Update .claude/settings.json deny list`,
`Fix User-Agent header parsing`, `Add reagent lookup table`,
`Update Gemini protocol client`, `[REQ] draft REQ-AI-001` (also `REQ-LLM-`,
`REQ-AGENT-`, area codes §3.1 invites adopters to choose). On a `claude/*`
branch, `git merge --no-edit development` is blocked at line 1
(`Merge branch 'development' into claude/step-x`) and leaves `MERGE_HEAD`
behind; `--squash`, `--log` and `--fixup` copy human-written subjects into the
message and get blocked too. Nothing documents the `-m "Merge development"`
workaround.

Change `.githooks/_agent.sh`:

```sh
# TUNABLE: words an agent commit message may never contain (POSIX ERE, word-bounded,
# case-insensitive).
FORBIDDEN_MSG_RE='(^|[^[:alnum:]_])(claude|anthropic|openai|chatgpt|copilot|gemini|codex|ai|llm|gpt|agents?|subagents?|agentic|co-authored-by|generated (with|by))([^[:alnum:]_]|$)|🤖'
# TUNABLE: harmless mentions removed before the scan: this repo's instruction files,
# the .claude/ directory, work-branch names (covers git's default merge subjects) and
# REQ/STEP ids. CLOUD_BRANCH_PREFIX is used inside an ERE: no regex metacharacters.
ALLOWED_MSG_RE="AGENTS\\.md|CLAUDE\\.md|\\.claude/[^[:space:]]*|${CLOUD_BRANCH_PREFIX}[^[:space:]']+|User-Agent|(REQ|STEP)-[A-Z0-9]+-[0-9]+"
```

and in `.githooks/commit-msg`:

```sh
scan=$(printf '%s\n' "$msg" | sed -E "s#$ALLOWED_MSG_RE##g")
hit=$(printf '%s\n' "$scan" | grep -inE "$FORBIDDEN_MSG_RE" | head -n 1)
```

Add self-tests: default merge message into `claude/*` (advance `development`
first so a merge commit is actually created), `Clarify push rule in AGENTS.md`,
`Fix User-Agent header parsing`, `[REQ] draft REQ-AI-001` all `ok`;
`Add AI model config`, `Generated with Claude Code` still `blocked`. Document
in `docs/GIT-WORKFLOW.md` that `--squash`, `--log` and `--fixup` copy other
people's text and may need a hand-written `-m`.

Related: AGENTS.md lists "assistant" as forbidden and names Cursor, but the regex
blocks neither. Do not add `assistant` to the regex (it would block
"Fix assistant role parsing" in any LLM-app project); instead align the three
lists (AGENTS.md §1, GIT-WORKFLOW.md, the regex comment) so they name the same
words and say the regex is the enforced subset.

### 1.2 Cloud sessions append a `Claude-Session:` trailer the hook blocks (priority 2)

The settings schema and https://code.claude.com/docs/en/settings-reference
document `attribution.sessionUrl` (default true in web/Remote Control
sessions). The trailer contains "claude" and is blocked. Reproduced. This
session received that very instruction and had to ignore it.

Change `.claude/settings.json`:

```json
"attribution": { "commit": "", "pr": "", "sessionUrl": false }
```

### 1.3 Hook tunables are environment-overridable (priority 5)

`PROTECTED_BRANCHES="${PROTECTED_BRANCHES:-main development}"` and friends mean
`PROTECTED_BRANCHES=none CLAUDECODE=1 git commit` on `main` succeeds, and
`CLOUD_BRANCH_PREFIX=m PROTECTED_BRANCHES=x git push origin claude/x:main`
succeeds in a cloud session. Reproduced. Nothing in the repo uses the override
(`test-hooks.sh` never sets them; the SETUP comments say to edit the file).

Change to plain assignments:

```sh
PROTECTED_BRANCHES="main development"
CLOUD_BRANCH_PREFIX="claude/"
MAX_SUBJECT_LEN=72
```

Add regression tests: `env PROTECTED_BRANCHES=x git commit` on `main` must stay
blocked; `cloud env CLOUD_BRANCH_PREFIX=m PROTECTED_BRANCHES=x git push origin claude/step-x:main` must stay blocked.

### 1.4 Cloud push exemption allows force-push and deletion of any `claude/*` branch; tags are pushable (priority 11)

Reproduced in cloud profile: `git push --force origin claude/step-x:claude/other-session`
overwrites a sibling session's branch; `git push origin :claude/other-session`
deletes it. With `AGENT_PUSH_APPROVED=1`, agents can push and delete tags
although AGENTS.md says tags are the user's; in cloud the refusal message for a
tag talks about branches.

Change `.githooks/pre-push`:

```sh
ZERO_SHA=0000000000000000000000000000000000000000
...
    case "$remote_ref" in
        refs/heads/*) name=${remote_ref#refs/heads/} ;;
        *) deny "agents may only push branches ('$remote_ref' refused); tags are the user's." ;;
    esac
    if is_protected "$name"; then deny "agents may not push to '$name'."; fi
    [ "${AGENT_PUSH_APPROVED:-}" = "1" ] && continue
    if is_cloud; then
        case "$remote_ref" in
            "refs/heads/$CLOUD_BRANCH_PREFIX"*)
                # Unasked cloud pushes may only create or fast-forward a branch;
                # rewriting or deleting one (possibly another session's) needs approval.
                [ "$local_sha" = "$ZERO_SHA" ] && deny "cloud session: deleting '$name' needs AGENT_PUSH_APPROVED=1."
                if [ "$remote_sha" != "$ZERO_SHA" ] && ! git merge-base --is-ancestor "$remote_sha" "$local_sha" 2>/dev/null; then
                    deny "cloud session: force-updating '$name' needs AGENT_PUSH_APPROVED=1."
                fi
                continue ;;
        esac
        deny "cloud session: agents may only push '$CLOUD_BRANCH_PREFIX*' branches ('$name' refused)."
    fi
```

Add tests (fast-forward ok, force blocked, approved force ok, delete blocked,
approved delete ok, tag push blocked for approved and cloud, human tag ok).
Update REQ-BUILD-002's acceptance criteria, the GIT-WORKFLOW.md pre-push row,
and AGENTS.md ("Open a PR only when the user asks; never merge, approve or
enable auto-merge").

### 1.5 Rebase, cherry-pick, revert and `am` run no protected-branch check

Reproduced with an agent on `main`: `git rebase feature/x`, `git cherry-pick`,
`git revert`, `git am`, `git switch -C main …`, `git branch -f development …`
all succeed; `cherry-pick`/`revert` also skip `commit-msg`, so their messages are
never scanned. GIT-WORKFLOW.md says `pre-commit` covers "also mid-rebase",
which is only true for an explicit `git commit` during a rebase stop.

Recommended (small, verified): add three hooks that reuse the `pre-commit`
rule, and list them in `setup.ps1`:

- `.githooks/pre-rebase`: `branch=${2:-$(current_branch)}; is_protected "$branch" && deny …`
- `.githooks/prepare-commit-msg` and `.githooks/pre-applypatch`: identical body
  to `pre-commit` (reached by `cherry-pick`/`revert` and by `am`).

Do **not** add a `reference-transaction` hook as the default: it aborts
`git gc`/`pack-refs`/`maintenance` for agents and blocks recovery commands.
Mention it as an opt-in with those caveats. Rewrite the "Known client-side
gaps" paragraph honestly: fast-forward merges and `pull`, `reset`,
`switch -C`, `branch -f`, `update-ref`, plumbing, and API writes run no hook;
messages of `cherry-pick -e`/`revert -e` are not scanned. Add an acceptance
criterion to REQ-BUILD-002 for the new hooks.

### 1.6 Subject-length check is locale-dependent

`wc -m` counts bytes under the POSIX locale, which is the default in the cloud
container (`LANG` unset). A 71-code-point subject containing an em dash and an
arrow (the house style of this repo's own docs) is rejected as 75 characters.
Reproduced.

Add to `_agent.sh` and use it in `commit-msg`:

```sh
# Code points, independent of the caller's locale (wc -m counts bytes under LANG=C).
char_count() { LC_ALL=C tr -d '\200-\277' | wc -c | tr -d ' '; }
```

### 1.7 `commit-msg` hardcodes `#` as the comment character

With `core.commentChar=';'`, every editor commit on a `claude/*` branch is
blocked on git's own template line (`; On branch claude/step-1`); conversely
`-m "# Generated with Claude"` is stored but never scanned. Reproduced.

Replace the stripping with git's own logic:

```sh
msg=$(sed '/^[^[:space:]]* -\{24\} >8 -\{24\}/,$d' "$1" | git stripspace --strip-comments)
```

Verified 28/28 against the self-test and across all legal comment chars on
git 2.43. Document the `-m "# …"` blind spot as a known gap (guard rail, not a
boundary).

### 1.8 `PROTECTED_BRANCHES` is subject to pathname expansion and has no glob support

`for _b in $PROTECTED_BRANCHES` expands `release/*` against the working tree:
with a file `release/1.0` present, only that name is protected. Reproduced.

```sh
is_protected() {
    set -f
    for _b in $PROTECTED_BRANCHES; do
        case "$1" in $_b) set +f; return 0 ;; esac
    done
    set +f; return 1
}
```

State in the comment that entries are shell patterns (`release/*`) and add a
test.

### 1.9 Smaller hook items

  the first body line).
- **IDE terminals.** Claude Code's VS Code/JetBrains extensions export

  `CLAUDE_CODE_CHILD_SESSION` is unset ("if you are a human in a Claude Code

- **Gemini CLI** documents `GEMINI_CLI=1` for the commands it runs

- **Worktrees.** A relative `core.hooksPath` is correct (per-worktree,

- **Enforcement files are editable by the agent** without any prompt
  (`.githooks/`, `scripts/setup.*`, `scripts/test-hooks.sh`,

## 2. Claude Code configuration

### 2.1 `ask` on `git push` vs "cloud may push without asking" (priority 7)

CLAUDE.md, AGENTS.md and GIT-WORKFLOW.md say a cloud session pushes its own
`claude/*` branches "without being asked"; `.claude/settings.json` has
`"ask": ["Bash(git push:*)"]`, which per
https://code.claude.com/docs/en/permission-modes prompts in every mode,
including auto, and matches past a leading `AGENT_PUSH_APPROVED=1`. Project
settings are read in single-repo cloud sessions. So the cloud agent waits at a
browser prompt the docs never mention, and the user may not be there.

Pick one and state it in all three files:

- **Keep the prompt (simplest):** reword to "Claude Code's permission prompt
  for `git push` still appears, also in cloud sessions, and is the user's
  confirmation; the pre-push hook is an independent second gate", and warn that
  a cloud session waits at that prompt until answered.
- **Unattended cloud pushes:** keep the `ask` rule and add a `PermissionRequest`
  hook (`"if": "Bash(git push *)"`) whose command prints
  `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}`
  only when `CLAUDE_CODE_REMOTE=true`; the pre-push hook still enforces the
  branch rules. Verify once that the installed Claude Code honours `if`.

### 2.2 Deny list is thin and GitHub API writes bypass hooks entirely

Reproduced bypasses not covered by the deny list: `git -c core.hooksPath=/dev/null commit`
(also lowercase `hookspath`), `GIT_CONFIG_PARAMETERS=…`, `GIT_CONFIG_COUNT/KEY/VALUE`,
`CLAUDECODE=0 git commit`, `env -u CLAUDECODE git commit`, `git commit -nm`,
`git commit -m x -n`. Separately, this session's own tool list contains
`mcp__github__push_files`, `create_or_update_file`, `delete_file`,
`merge_pull_request`, `enable_pr_auto_merge`: they write to the repository over
the API from the agent's identity, no client hook runs, and no rule mentions
them. AGENTS.md reserves "PR merges" for the user but nothing enforces it.

Add to `permissions.deny` (all schema-valid; globs are allowed in deny/ask):

```json
"Bash(git commit -n*)", "Bash(git commit * -n)", "Bash(git commit * -n *)",
"Bash(git * --no-verify*)",
"Bash(git config core.hooksPath*)", "Bash(git config --local core.hooksPath*)",
"Bash(git config --global core.hooksPath*)", "Bash(git config --unset core.hooksPath*)",
"Bash(git -c *)", "Bash(git -C *)",
"Bash(env -u CLAUDECODE*)", "Bash(env -u AGENT_SESSION*)", "Bash(env -i *)",
"Bash(unset CLAUDECODE*)", "Bash(unset AGENT_SESSION*)",
"Bash(export CLAUDE_CODE_REMOTE*)", "Bash(export AGENT_PUSH_APPROVED*)",
"mcp__*__push_files", "mcp__*__create_or_update_file", "mcp__*__delete_file",
"mcp__*__merge_pull_request", "mcp__*__enable_pr_auto_merge", "Bash(gh pr merge:*)"
```

and to `permissions.ask`: `"mcp__*__create_pull_request"`, `"Bash(gh pr create:*)"`.
Do not use `Bash(git * core.hooksPath*)`: it also denies the read-only
`git config --get core.hooksPath` that AGENTS.md tells agents to run. Soften
CLAUDE.md "forbids hook bypasses" to "blocks the usual hook-bypass spellings",
and extend "Known client-side gaps" with the `-c`/`GIT_CONFIG_*`/env-unset
forms and "API writes never run client hooks; only server-side rulesets apply".
A `PreToolUse` hook that inspects the full command text is the real
client-side option if an adopter wants more than best effort.

### 2.3 Secrets in `.env` are readable without a prompt

`cat`, `head`, `sed` are built-in read-only commands that never prompt, and
there are no `Read` deny rules. Add `"Read(./.env)"` and `"Read(./*.local.env)"`
to `permissions.deny`. Do not add `Read(./.env.*)` (it would block the
committed `.env.example`) or `Read(./.claude/settings.local.json)` (a Read
deny also blocks Edit/Write, and CLAUDE.md designates that file for personal
settings).

  Definition-of-done boxes and promotes REQ statuses; Claude should not decide

  `trace-regenerate` invocable: `step-complete` calls it as a sub-step, and a

## 3. Process documents

### 3.1 Branch creation fails in fresh clones; no `development` branch (priority 3)

`step-start` (and §5.4 step 2, AGENTS.md, GIT-WORKFLOW.md) say
`git switch -c claude/<STEP-ID>-<slug> development`. After any `git clone`,
`development` exists only as `origin/development`, and git does not DWIM a
remote-tracking branch as a start point for `-c`: "fatal: invalid reference:
development". Reproduced for full, single-branch and shallow clones. This repo
itself has no `development` branch (only `main`), so the command fails even
after a fetch.

Change the command everywhere to:

```sh
git fetch origin development:refs/remotes/origin/development && \
git switch -c claude/<STEP-ID>-<slug> --no-track origin/development
```

and add: "if the fetch fails, stop and tell the user that `development`
(README step 1) does not exist yet; do not fall back to `main`". Create the
`development` branch in this repository so "Use this template, include all
branches" matches README step 1. Optionally have `scripts/setup.sh` warn when
`git ls-remote --heads origin development` is empty.

### 3.2 Scan roots miss the seed REQs' tags (priority 6)

§3.2 requires an `implements:` tag "in the code root" (`src/`, which does not
exist) and a `verifies:` tag in the test root (`tests/`). The shipped tags live
in `dev`, `dev.ps1`, `.github/workflows/ci.yml`, `.githooks/_agent.sh` (not in
any scanned location) and `scripts/test-hooks.sh` (not a test root). Read
literally, REQ-BUILD-001/002 can never become `implemented`, and REQ-BUILD-002
never `verified`.

Edit REQUIREMENTS-MANAGEMENT.md: §3.2 "≥ 1 `implements:` tag in a scanned code
location (§4.2)" and "≥ 1 `verifies:` tag in a scanned test location (§4.2)";
§4.2 add `.githooks/` to "Also scanned for `implements:`" and a new bullet
"**Also scanned for `verifies:` / `supports:`:** `scripts/`"; §4.1 diagram
"scanned locations"; §4.3 step 3 reads both lists.

### 3.3 `TRACE.md` regeneration: conflicts and reproducibility (priority 12)

§5.4 step 9 regenerates `TRACE.md` on every work branch with a stamp of
"date, branch, short HEAD SHA, one-paragraph summary". Reproduced: two work
branches that each followed §5.4 conflict on `TRACE.md` when the second merges
into `development`. The WIP limit check only sees its own branch, so with N
agents the effective limit is 2N. An LLM-authored matrix is also not
"reproducible from a fresh scan" (§1 rule 2, §8), and the scan configuration
lives in prose, which is how 3.2 went unnoticed.

Recommended: a stdlib-only `scripts/trace.py` with `--coverage` (read-only
report plus proposed §3.2 transitions), default write mode, and `--check`
(diff only the deterministic body; exit 1 when stale, for CI on `development`).
Scan roots become constants at the top of the script, pointed to from §4.2.
The agent still performs step 5 (transitions, after tests pass) and step 7.
Make the stamp a single reproducible line (date plus a computed delta such as
`REQ-BUILD-002 approved->implemented; +1 REQ`), no branch/SHA/history, so two
branches rarely touch the same hunk; document "on conflict, take either side
and regenerate". Wire `./dev trace`, add `python3 scripts/trace.py --check` to
the `hooks` CI job, commit a real generated `TRACE.md` for the two seed REQs
instead of the "Generated: never" stub, and state the python3 dependency.
Define WIP against the integration view (steps in `doing/` on `development`
plus open work-branch PRs).

### 3.4 `DEV_CONFIGURED` gate is undocumented (priority 8)

`ci.yml` skips `build-test` unless the repository variable `DEV_CONFIGURED`
is `true`; nothing else mentions the variable. `./dev ci` runs
build/check/test unconditionally and fails as shipped ("'build' is not
configured yet"), while CI is green, so REQ-BUILD-001's "`./dev ci` runs the
same steps as ci.yml" is false and the PR checklist "Tests pass locally
(`./dev ci`)" cannot be ticked. A job skipped by `if:` satisfies a required
status check.

Keep the gate (it keeps template and fresh-adopter CI meaningfully green) and
describe it: in the `ci.yml` SETUP comment (how to set the variable, delete the
`if:` once configured, skipped jobs count as passing), in README step 3, in
GIT-WORKFLOW.md ("require the checks `git hooks self-test` and
`build & unit tests` by job name; remove the gate before relying on the
second"), and reword the REQ-BUILD-001 criterion to "… as the `build-test` job
once that job is enabled".

### 3.5 Text inconsistencies (all small)

- §3.3 says a meaning-changing edit "resets `status` to `draft`", but the
  §3.2 table has no `→ draft` row, and §6.2 step 5 sets the edited REQ to
  `needs-reverify`. Add the row (who: whoever makes the edit, during §6.2 step
  5; precondition: report approved) and state in §6.2 step 5 that the edited
  REQ goes to `draft` and the affected set to `needs-reverify`; §6.2 step 6:
  the edited REQ stays `draft` until a human re-approves.
- §3.2 "every step whose `implements` lists this REQ is in `done/`" counts
  cancelled steps and `STEP-<My>-000` placeholders, contradicting §5.2

## 4. Task runner and Windows

- **`./dev.ps1 ci` fails on a default Git for Windows install** (priority 10):
  `Run sh scripts/test-hooks.sh` needs `sh` on PATH, but the installer's
  default PATH option adds only `<Git>\cmd` (`usr\bin` is the optional
  "Unix tools" choice; verified against `install.iss`). Resolve `sh` next to
  `git.exe`:

  ```powershell
  function Get-Sh {
      $sh = Get-Command sh -ErrorAction SilentlyContinue
      if ($sh) { return $sh.Source }
      $git = Get-Command git -ErrorAction SilentlyContinue
      if ($git) {
          $cand = Join-Path (Split-Path (Split-Path $git.Source)) 'bin\sh.exe'
          if (Test-Path $cand) { return $cand }
      }
      Die 'sh not found: install Git for Windows or add <Git>\usr\bin to PATH'
  }
  ```

- **`Run` trusts a stale `$LASTEXITCODE`.** It is only set by native
  executables; for a cmdlet, function or `.ps1` the previous value is reused,
  so failures are missed or successes reported as failures (reproduced under
  pwsh 7.4). Reset it and also check `$?`:

  ```powershell
  $global:LASTEXITCODE = 0
  & $args[0] @rest
  $ok = $?
  if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }
  if (-not $ok) { exit 1 }
  ```

- **Execution policy.** Windows PowerShell 5.1 defaults to `Restricted`; no
  `.ps1` runs. README step 2 should say
  `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/setup.ps1` (or
  `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` once). `Invoke-Setup`
  should run the script in-process (`Run (Join-Path $PSScriptRoot 'scripts/setup.ps1')`)
  instead of spawning `powershell`, which also makes it work under `pwsh` on
  macOS/Linux.
- **`Set-Location $PSScriptRoot` leaks** into the caller's shell (a `.ps1`
  shares the session's location). Use `Push-Location` with `try/finally { Pop-Location }`
  around the dispatch (reproduced).
- **`.env` semantics differ**: `./dev` executes it (`source` with `set -a`;
  `FOO=bar baz` aborts with exit 127, `$(…)` runs, `it's` is a syntax error),
  `dev.ps1` parses it as text. Parse the same `KEY=value` subset in bash
  (a `while read` loop with a regex match, strip matching quotes, tolerate
  CRLF) and document the grammar in `.env.example` ("not executed; no `export`,
  no `$VAR`, no inline comments").
- **`scripts/setup.sh` dirties the tree** (priority 4): `chmod +x .githooks/*`
  flips `_agent.sh` to 755; `setup.ps1` and `test-hooks.sh` deliberately
  exclude `_*`. Use `chmod +x .githooks/[!_]* dev scripts/*.sh` with a comment.
- **`setup.ps1` lists executables by name**, so a hook added on Windows (such
  as `pre-rebase` above) is not marked. Derive the list from the index:
  `$exec = git ls-files -- '.githooks/[!_]*' dev 'scripts/*.sh'; if ($exec) { git update-index --chmod=+x -- $exec }`.
- `.gitattributes` `dev text eol=lf` is unanchored and matches any `dev` at
  any depth (`git check-attr` confirms); write `/dev`.

## 5. CI and GitHub settings

- **Token permissions and action pinning** (priority 9): add
  `permissions: contents: read` at workflow level; CI runs code from any pushed
  branch, including agent branches, with the repository's default token. Pin
  `actions/checkout` to a SHA (`3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`;
  v4 runs on Node 20, deprecated by the runner since June 2026), add
  `persist-credentials: false` on the `hooks` job's checkout, and add
  `.github/dependabot.yml` (`package-ecosystem: github-actions`, monthly) so
  the pin stays current.
- **Double runs**: `on: push` (unfiltered) plus `pull_request` runs every PR
  commit twice (different `github.ref`, so the concurrency group does not
  dedupe). Use `push: branches: [main, development]` plus `pull_request`, and
  say in GIT-WORKFLOW.md that a work branch is checked once its PR exists.
- **`cancel-in-progress: true` also cancels runs on `main`/`development`**,
  leaving merge commits without a CI result. Use
  `cancel-in-progress: ${{ github.ref != 'refs/heads/main' && github.ref != 'refs/heads/development' }}`.

  already needed a "Windows commit fix". Add a `windows-latest` job running
  `./dev.ps1 help`, `./dev.ps1 setup` (pwsh) and `sh scripts/test-hooks.sh`

- **Server-side protection section is inaccurate.** Rulesets and branch

  updates), say that the bypass list must contain humans only (never the

  ruleset once agent tag pushes are refused client-side.
